# 数据留存期限与过期清理（dsh-data-lifecycle）

**什么时候用**：想确认「数据是不是留太久了、该删的有没有删」。
用户会说：「数据留存多久」「留存期限」「数据生命周期」「有没有过期清理」「该删的删了吗」「数据是不是一直躺着」。

## 怎么用

```bash
dsh-data-lifecycle --root <项目目录>
```

（把 `<cli 路径>` 交给插件注册后，命令名由 DSH 插件系统提供；本地调试也可直接 `node bin/cli.mjs --root <目录>`。）

## 怎么读结果

5 条规则，分三类问题：

1. **说不清留多久**（`LIFE-NO-RETENTION-POLICY`）——代码、配置、文档里都没有留存期限。
   先问一句：这个项目里的数据，谁负责让它消失？没有答案就先补一张表。
2. **留太久**（`LIFE-RETENTION-TOO-LONG`）——3 年以上 / 1095 天以上。
   个保法第 19 条要的是「最短必要」，不是「越久越安全」。确实需要长期保存的，写清法律依据。
3. **只写不删**（`LIFE-WRITE-NO-PURGE` / `LIFE-SCHEDULE-NO-CLEANUP` / `LIFE-SCHEMA-NO-EXPIRY-FIELD`）——
   写入路径齐全，清理路径缺失；或者有定时任务但没一个是清理。
   补一条可被调度的清理路径，并把清理条数写进日志，方便事后自查。

## 与相邻插件的分界

| 插件 | 它管什么 |
|---|---|
| `dsh-cn-log-retention` | 日志留存**够不够** 6 个月（下限，网络安全法第 21 条） |
| **本插件** | 数据留**多久**、到期有没有人删（个保法第 19 / 47 条） |
| `dsh-data-classify` | 数据分没分级、有没有台账 |
| `dsh-data-rights` | 用户来要求删除时，删不删得掉 |
| `dsh-pipia` | 影响评估报告本身要不要留三年（个保法第 56 条） |

## 不要做什么

- 不要把「命中」当成「违规」—— 长期保存可能有法律依据，命中只是提示你确认
- 不要指望它替你删数据 —— 它是静态检查，不碰你的库和文件
- 不要因为「0 命中」就放心 —— 清理完全做在部署层或 DBA 流程里时，它看不见
